## Part A — 设计方法论补充

### A.1 文档骨架（完整章节清单）

契约文档的**完整**章节顺序建议（比 R6 基线与 `contract-template.md` 更全，供含事件 / Slots / Ref / 组合规则 / 响应式的复杂组件增补）：

0. 元信息（组件名 / 分类 / 版本 / 状态 / 负责人 / 最后更新 / 关联文档）
1. 概述（用途 / 使用场景 / 不适用场景）
2. 设计变体映射（尺寸 / 变体 → Props 枚举 → 说明；含尺寸映射表）
3. Props（表格：名称 / 类型 / 默认值 / 必填 / 受控 / 枚举 / 说明）
4. 事件（表格：名称 / 触发时机 / 参数 / 是否可取消 / disabled 时 / 说明）
5. Slots / Children（表格）
6. Ref 方法（React 19 普通 ref；类型 / 暴露能力 / 不暴露项）
7. 状态矩阵（列定义见 A.2）
8. 组合规则（表格：组合 / 是否允许 / 视觉规则 / 说明）
9. 可访问性（语义角色 / 键盘 / ARIA 属性表 / 对比度 / SR 播报 / 动效）
10. 响应式（表格）
11. 使用示例（代码块，受控 / 非受控 / 尺寸 / 错误态）

- 附录 A：设计决策（表格：决策点 / 结论 / 依据）
- 附录 B：待核对风险 + 落地说明（执行层面，非契约正文）

> **三层关系**：R6 是**建议基线**（概述 / Props / 状态与变体 / 尺寸 / 样式映射 / 可访问性 / 使用示例 / FAQ / 变更记录），`contract-template.md` 是**精简落地骨架**，本清单是**完整骨架**。
> 可据组件类型增删或调序，但保持「契约正文 → 附录（决策 / 风险 / 落地）」的分层；**模板既有章节名不可擅改**（铁律 1），需要新增的章节（事件 / Slots / Ref / 组合规则 / 响应式 / 附录）在模板允许的前提下追加，否则写入项目 MVP 清单并在「变更记录」留指向。

### A.2 视觉描述表标准列

状态矩阵 / 变体表等"视觉展示"表格，**统一列**：`视觉效果` / `Figma 变量名` / `Tailwind 工具类` / `设计稿`（必要时追加 `交互行为`）。

> **与 R1 的分工**：R1 管的是「CSS Token 映射表」（`figma 变量名` / `tailwind 工具类` / `对应的 css 值` 三列）；本条管的是「视觉展示表」，它多出 `视觉效果` 与 `设计稿` 两列，用于表达状态外观与设计稿出处。**两张表的列定义不要混用**。
> 落地时先对齐仓库内既有同类组件文档的表头，避免每次重发明。

### A.3 决策先问用户（不要替用户硬定）

遇到需拍板的设计点（配色维度、是否引入组合组件、尺寸阶梯、滑块表达等）：

1. 先在文档 / 回复中给出各方案：**区别 / 优点 / 缺点 / 推荐方案 / 推荐理由**。
2. 再用 `AskUserQuestion` 收口（用户可写"先看详细利弊"）。
3. 把争议与推荐写进附录「设计决策」或「待裁决决策」节。

### A.4 控件 vs 组合组件边界

- 保持组件**纯净**：错误态 / 表单校验 / label 组合等"组合"能力，优先走契约**外**机制（如调用方设置 `aria-invalid`、自行包 `<label>`），不在本组件内引入 `*Field` 类包装。
- 如用户明确要求"只做纯控件、不要 Field 相关设计"，**全面移除**方案中所有 Field / 组合内容。

### A.5 流程纪律

- 设计阶段只产出**本地**规划 / 文档（如 `xxx-contract-design.md`）。
- **不回写飞书直到用户明确要求**。回写前先就设计内容达成一致。

## Part B — 飞书回写 SOP

### B.1 前置

本地先准备好一份干净的 Markdown 正本（如 `switch-api-contract-design.md`）。**上传用临时文件**建议单开（如 `_upload.md`），因为上传前需做转义处理（B.3），处理后正本与上传件可不同。上传成功并核验后再清理临时文件。

### B.2 命令形态

```bash
# 回写（覆盖）到飞书 wiki/docx
lark-cli docs +update --doc "<wiki 或 docx URL>" \
  --command overwrite --doc-format markdown \
  --content @./_upload.md --as user

# 回读核验（全文）
lark-cli docs +fetch --doc "<URL>" --scope full --format pretty
```

关键点：

- URL **必须走 `--doc` 参数**，不能做位置参数，否则报 `positional arguments are not supported`。
- `fetch` 的 `--format` **不接受 `markdown`**，只认 `json | pretty | table | ndjson | csv`；用 `pretty` 拿 DocxXML 全文核对内容。
- `--content @./file.md` 的 `@` 前缀表示读取文件内容。

### B.3 上传前：`<tag>` 剥离坑与转义（最关键）

飞书 markdown→DocxXML 转换器会把 `<...>` 当作 HTML 标签**剥离**（仅保留内部文本），且：

- 反斜杠转义 **仅在裸文本生效**（如 `React.Ref\<HTMLInputElement\>` 安全）。
- **反引号代码内**的 `\<input\>` 不被识别为转义，仍被剥离。
- **fenced 代码块**（` ```tsx `）内的 `<Switch .../>` 不受影响，整体保留为代码，**无需处理**。

转义对照表：

| 场景          | 原内容                        | 改为                                           |
| ------------- | ----------------------------- | ---------------------------------------------- |
| 裸文本泛型    | `React.Ref<HTMLInputElement>` | `React.Ref\<HTMLInputElement\>`                |
| 反引号内标签  | ``隐藏 `<input>` 的 ref``     | `隐藏 \<input\> 的 ref`（去掉反引号，裸转义）  |
| 反引号内标签  | `` 内置 `<span>` ``           | `内置 \<span\>`                                |
| 路径占位符    | `color/<layer>/<semantic>`    | `color/{layer}/{semantic}`（花括号规避尖括号） |
| fenced 代码块 | ` ```tsx <Switch .../> ``` `  | 原样保留（不处理）                             |

处理完用 grep 自检：文档内所有应在飞书显示为字面量的 `<` 都应是 `\<`（裸文本）或已被替换；fenced 块内除外。

### B.4 回读核验清单

`overwrite` 返回的 `warnings` 可能**不穷尽**所有被剥标签（只报部分）。必须 `fetch --format pretty` 回读，确认：

1. 标题 / 所有章节（`&lt;h1&gt;`~`&lt;h2&gt;` 等）齐全，无缺失。
2. 所有字面量标签渲染为 `&lt;…&gt;`（未被吞）。
3. 表格、代码块、列表结构完整。

`warnings: []` 且回读内容完整 = 回写干净。

### B.5 清理

核验无误后删除上传临时文件（`_upload.md`）与 `/tmp` 下中间物。本地规范正本保留。
